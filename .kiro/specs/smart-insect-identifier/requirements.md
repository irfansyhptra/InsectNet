# Requirements Document

## Introduction

The Smart Insect Identifier & AI Insights platform is an AI-powered web application that enables users to identify insect species by uploading images. The system uses a pre-trained PyTorch model for species classification and integrates Google Gemini API to provide educational insights about identified insects. The platform must deliver a premium user experience comparable to Google Lens and Linear, with graceful degradation when external services are unavailable.

## Glossary

- **System**: The complete Smart Insect Identifier platform (frontend + backend + ML model + external APIs)
- **Backend**: FastAPI server providing REST API endpoints for predictions, insights, and history
- **Frontend**: Next.js web application providing the user interface
- **ML_Service**: Backend service responsible for loading the PyTorch model and performing inference
- **Gemini_Service**: Backend service responsible for communicating with Google Gemini API
- **History_Service**: Backend service responsible for storing and retrieving prediction records
- **Prediction**: Classification result containing species name, confidence score, and top alternatives
- **AI_Insight**: Educational content about an insect species generated by Google Gemini API
- **User**: Person interacting with the web application to identify insects
- **Model**: Pre-trained PyTorch model located at backend/artifacts/model.pth
- **Confidence_Score**: Numerical value between 0 and 1 indicating prediction certainty
- **Top_Predictions**: Ordered list of most likely species with confidence scores
- **Upload_Workflow**: Five-step process: drag/drop → preview → analyze → results → insights
- **Graceful_Degradation**: System behavior that maintains core functionality when optional services fail
- **Health_Endpoint**: API endpoint that reports system operational status

## Requirements

### Requirement 1: Model Deployment and Loading

**User Story:** As a system administrator, I want the PyTorch model loaded once at startup, so that inference performance is optimized and resources are conserved.

#### Acceptance Criteria

1. WHEN the Backend starts, THE ML_Service SHALL load the Model from backend/artifacts/model.pth exactly once
2. THE ML_Service SHALL retain the loaded Model in memory as a singleton instance
3. THE ML_Service SHALL NOT reload the Model for individual prediction requests
4. IF the Model file is missing at startup, THEN THE Backend SHALL log an error and fail to start
5. THE ML_Service SHALL load model metadata from backend/artifacts/metadata.json
6. THE ML_Service SHALL load class labels from backend/artifacts/labels.json

### Requirement 2: Image Upload and Validation

**User Story:** As a user, I want to upload insect images through drag-and-drop or file selection, so that I can easily submit images for identification.

#### Acceptance Criteria

1. THE Frontend SHALL accept image uploads via drag-and-drop interaction
2. THE Frontend SHALL accept image uploads via file picker dialog
3. THE Frontend SHALL validate uploaded files are PNG, JPG, JPEG, or WEBP format
4. IF an invalid file format is uploaded, THEN THE Frontend SHALL display an error message
5. WHEN an image is uploaded, THE Frontend SHALL display a preview before analysis
6. THE Frontend SHALL allow users to remove or replace uploaded images before analysis
7. THE Frontend SHALL limit uploaded image file size to 10 megabytes

### Requirement 3: Image Preprocessing and Inference

**User Story:** As a developer, I want the ML service to preprocess images consistently, so that inference accuracy matches training conditions.

#### Acceptance Criteria

1. WHEN an image is received, THE ML_Service SHALL preprocess the image to match Model input requirements
2. THE ML_Service SHALL resize images to the dimensions expected by the Model
3. THE ML_Service SHALL normalize pixel values according to Model training parameters
4. THE ML_Service SHALL apply the same transformations used during Model training
5. THE ML_Service SHALL run inference on the preprocessed image tensor
6. THE ML_Service SHALL return a Prediction containing species name and Confidence_Score
7. THE ML_Service SHALL return Top_Predictions with at least five alternative species

### Requirement 4: Prediction API Endpoint

**User Story:** As a frontend developer, I want a REST API endpoint for predictions, so that I can submit images and receive classification results.

#### Acceptance Criteria

1. THE Backend SHALL expose a POST endpoint at /api/predict
2. WHEN a valid image is posted to /api/predict, THE Backend SHALL return a Prediction within 3 seconds
3. THE Backend SHALL return JSON containing species, confidence, and top_predictions fields
4. THE Backend SHALL return HTTP 400 if the image format is invalid
5. THE Backend SHALL return HTTP 500 if inference fails
6. THE Backend SHALL include proper CORS headers for Frontend requests
7. THE Backend SHALL validate image data before passing to ML_Service

### Requirement 5: AI Insights Generation

**User Story:** As a user, I want educational insights about identified insects, so that I can learn about their characteristics, habitat, and behavior.

#### Acceptance Criteria

1. WHEN a species is identified, THE Gemini_Service SHALL request AI_Insight from Google Gemini API
2. THE Gemini_Service SHALL format prompts to request taxonomy, habitat, behavior, and identification tips
3. THE Gemini_Service SHALL return AI_Insight as markdown-formatted text
4. THE Gemini_Service SHALL parse and structure the Gemini API response
5. THE Gemini_Service SHALL set a timeout of 10 seconds for Gemini API requests
6. THE Backend SHALL expose a POST endpoint at /api/insights accepting species name as input
7. THE Backend SHALL return markdown-formatted AI_Insight content

### Requirement 6: Graceful Degradation for AI Insights

**User Story:** As a user, I want to see prediction results even when AI insights are unavailable, so that I can still identify insects when external services fail.

#### Acceptance Criteria

1. IF the Gemini_Service receives HTTP 503 from Gemini API, THEN THE System SHALL display predictions without AI_Insight
2. IF the Gemini_Service times out, THEN THE System SHALL display predictions without AI_Insight
3. IF the Gemini_Service encounters rate limiting, THEN THE System SHALL display predictions without AI_Insight
4. WHEN AI_Insight is unavailable, THE Frontend SHALL display "AI insights temporarily unavailable" message
5. THE Frontend SHALL NOT crash or block user interaction when Gemini_Service fails
6. THE Gemini_Service SHALL implement retry logic with exponential backoff for transient failures
7. THE Gemini_Service SHALL log all Gemini API failures with error codes and timestamps

### Requirement 7: Prediction History Storage and Retrieval

**User Story:** As a user, I want to view my previous insect identifications, so that I can review past results and track my observations.

#### Acceptance Criteria

1. WHEN a Prediction is generated, THE History_Service SHALL store the image, species name, Confidence_Score, and timestamp
2. THE Backend SHALL expose a GET endpoint at /api/history
3. WHEN /api/history is requested, THE Backend SHALL return all stored prediction records in reverse chronological order
4. THE Backend SHALL return history records as JSON array with image URL, species, confidence, and date fields
5. THE Frontend SHALL display prediction history in a searchable grid layout
6. THE Frontend SHALL allow users to filter history by species name
7. THE Frontend SHALL allow users to filter history by date range

### Requirement 8: Health Check and System Monitoring

**User Story:** As a system administrator, I want a health check endpoint, so that I can monitor system availability and diagnose issues.

#### Acceptance Criteria

1. THE Backend SHALL expose a GET endpoint at /api/health
2. WHEN /api/health is requested, THE Backend SHALL return HTTP 200 if all services are operational
3. THE Backend SHALL verify Model is loaded in memory during health checks
4. THE Backend SHALL include model_loaded, gemini_available, and database_connected status fields
5. THE Backend SHALL return HTTP 503 if critical services are unavailable
6. THE Health_Endpoint SHALL respond within 500 milliseconds
7. THE Health_Endpoint SHALL NOT trigger inference or external API calls

### Requirement 9: Upload Workflow User Experience

**User Story:** As a user, I want a clear step-by-step workflow for uploading and analyzing images, so that I understand the process and system status.

#### Acceptance Criteria

1. THE Frontend SHALL implement the Upload_Workflow with five distinct steps
2. WHEN a user uploads an image, THE Frontend SHALL transition from upload to preview step
3. WHEN a user clicks analyze, THE Frontend SHALL display "Analyzing image..." loading message
4. WHILE analysis is in progress, THE Frontend SHALL display "Detecting species..." status message
5. WHILE insights are being generated, THE Frontend SHALL display "Generating AI insights..." status message
6. THE Frontend SHALL use skeleton loaders and progress animations during loading states
7. THE Frontend SHALL use Framer Motion for smooth transitions between workflow steps

### Requirement 10: Prediction Results Display

**User Story:** As a user, I want to see detailed prediction results including species name, confidence, and alternatives, so that I can understand identification certainty.

#### Acceptance Criteria

1. WHEN a Prediction is complete, THE Frontend SHALL display the species name prominently
2. THE Frontend SHALL display the scientific name below the common name
3. THE Frontend SHALL display the Confidence_Score as a percentage
4. THE Frontend SHALL display Top_Predictions with horizontal probability bars
5. THE Frontend SHALL display taxonomy information in a card layout
6. THE Frontend SHALL display prediction timestamp
7. THE Frontend SHALL allow users to copy species name to clipboard

### Requirement 11: AI Insights Rendering

**User Story:** As a user, I want AI insights rendered with proper formatting, so that educational content is readable and well-structured.

#### Acceptance Criteria

1. WHEN AI_Insight is available, THE Frontend SHALL render markdown content using react-markdown
2. THE Frontend SHALL support headings, lists, tables, quotes, and code blocks in rendered markdown
3. THE Frontend SHALL apply consistent typography and spacing to rendered content
4. THE Frontend SHALL display AI_Insight in a dedicated section below prediction results
5. THE Frontend SHALL distinguish AI-generated content from prediction data visually
6. THE Frontend SHALL handle empty or malformed markdown gracefully
7. THE Frontend SHALL render AI_Insight with proper syntax highlighting for code blocks

### Requirement 12: Dark Theme Design System

**User Story:** As a user, I want a modern dark-themed interface, so that the application is comfortable to use and visually appealing.

#### Acceptance Criteria

1. THE Frontend SHALL use background color #09090B for the main application background
2. THE Frontend SHALL use color #111827 for card components
3. THE Frontend SHALL use color #10B981 as the primary accent color
4. THE Frontend SHALL use color #14B8A6 as the secondary accent color
5. THE Frontend SHALL use color #3B82F6 for additional accent elements
6. THE Frontend SHALL use Inter font family as the primary typeface
7. THE Frontend SHALL maintain WCAG AA contrast ratios for all text and interactive elements

### Requirement 13: Responsive Layout and Accessibility

**User Story:** As a user with accessibility needs, I want the interface to support keyboard navigation and screen readers, so that I can use the application effectively.

#### Acceptance Criteria

1. THE Frontend SHALL support keyboard navigation for all interactive elements
2. THE Frontend SHALL provide visible focus indicators with 2-pixel outline
3. THE Frontend SHALL include ARIA labels for screen reader compatibility
4. THE Frontend SHALL maintain responsive layout from 320px to 3840px viewport width
5. THE Frontend SHALL provide text alternatives for all images and icons
6. THE Frontend SHALL ensure all interactive elements have minimum 44x44 pixel touch targets
7. THE Frontend SHALL support browser zoom up to 200 percent without layout breaking

### Requirement 14: Performance and Loading Optimization

**User Story:** As a user, I want fast page loads and responsive interactions, so that the application feels snappy and professional.

#### Acceptance Criteria

1. THE Frontend SHALL achieve First Contentful Paint within 1.5 seconds on 3G networks
2. THE Frontend SHALL lazy-load images in prediction history
3. THE Frontend SHALL implement code splitting for route-based components
4. THE Backend SHALL respond to /api/predict requests within 3 seconds for images under 5 megabytes
5. THE Frontend SHALL display loading skeletons within 100 milliseconds of user action
6. THE Frontend SHALL optimize images for web display before upload
7. THE System SHALL implement caching headers for static assets

### Requirement 15: Error Handling and User Feedback

**User Story:** As a user, I want clear error messages when something goes wrong, so that I understand what happened and how to proceed.

#### Acceptance Criteria

1. WHEN an error occurs, THE Frontend SHALL display a user-friendly error message
2. THE Frontend SHALL distinguish between network errors, validation errors, and server errors
3. IF the Backend is unreachable, THEN THE Frontend SHALL display "Unable to connect to server" message
4. IF image upload fails, THEN THE Frontend SHALL display "Upload failed, please try again" message
5. THE Frontend SHALL provide actionable suggestions in error messages
6. THE Backend SHALL return structured error responses with error codes and descriptions
7. THE Frontend SHALL log errors to browser console for debugging purposes

### Requirement 16: Clean Architecture and Service Separation

**User Story:** As a developer, I want clear separation between ML, Gemini, and History services, so that the codebase is maintainable and testable.

#### Acceptance Criteria

1. THE ML_Service SHALL contain only model loading, preprocessing, and inference logic
2. THE Gemini_Service SHALL contain only Gemini API communication logic
3. THE History_Service SHALL contain only data persistence and retrieval logic
4. THE ML_Service SHALL NOT make external API calls to Gemini
5. THE Gemini_Service SHALL NOT perform image inference
6. THE Backend SHALL implement dependency injection for service instances
7. THE Backend SHALL organize code into routes, services, schemas, and utils directories

### Requirement 17: Frontend Component Architecture

**User Story:** As a frontend developer, I want reusable components organized by feature, so that I can maintain and extend the UI efficiently.

#### Acceptance Criteria

1. THE Frontend SHALL organize components into upload, prediction, taxonomy, insights, charts, history, and ui directories
2. THE Frontend SHALL implement custom hooks for API communication
3. THE Frontend SHALL separate API logic into service layer modules
4. THE Frontend SHALL define TypeScript interfaces for all data structures
5. THE Frontend SHALL implement presentational and container component patterns
6. THE Frontend SHALL use Shadcn UI components for base UI elements
7. THE Frontend SHALL configure Tailwind CSS with custom design tokens

### Requirement 18: Configuration and Environment Management

**User Story:** As a developer, I want environment-specific configuration, so that I can deploy to different environments without code changes.

#### Acceptance Criteria

1. THE Backend SHALL load configuration from environment variables
2. THE Backend SHALL provide a .env.example file documenting required variables
3. THE Backend SHALL require GEMINI_API_KEY environment variable for Gemini_Service
4. THE Backend SHALL use configurable ports and host addresses
5. THE Frontend SHALL configure API base URL via environment variables
6. THE System SHALL NOT commit secrets or API keys to version control
7. THE Backend SHALL validate required environment variables at startup

### Requirement 19: API Documentation and Developer Experience

**User Story:** As a developer, I want API documentation, so that I can understand endpoints and integrate with the backend.

#### Acceptance Criteria

1. THE Backend SHALL expose OpenAPI documentation at /docs endpoint
2. THE Backend SHALL include request and response schemas in API documentation
3. THE Backend SHALL document expected error codes and responses
4. THE Backend SHALL provide example requests and responses in documentation
5. THE Backend SHALL include authentication requirements if implemented
6. THE Backend SHALL version API endpoints for future compatibility
7. THE Backend SHALL document rate limits and usage quotas

### Requirement 20: Logging and Debugging

**User Story:** As a developer, I want structured logging, so that I can diagnose issues in production.

#### Acceptance Criteria

1. THE Backend SHALL log all incoming API requests with timestamp and endpoint
2. THE Backend SHALL log inference duration and results
3. THE Backend SHALL log Gemini API requests and responses
4. THE Backend SHALL log errors with stack traces and context
5. THE Backend SHALL support configurable log levels via environment variables
6. THE Backend SHALL output logs in JSON format for log aggregation systems
7. THE Backend SHALL NOT log sensitive information such as API keys or user images
